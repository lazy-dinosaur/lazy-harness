## domain describe — 사용자 확정 계약

사용자 A안 선택 후 `방금 정한 거 knowledge_record로 남기고 구현해 줘.`로 실행 승인. 이유: 기존 도메인의 설명 편집으로 변경 범위를 제한하고 기존 관리 응답을 유지한다.
- `knowledge_cli.py domain` JSON 입력: `action=describe`, `domain`, `description`; `host_id` 생략 시 기존 default_host 사용.
- 지정 호스트의 기존 활성 도메인만 편집한다. 없는/폐기된 도메인은 오류이며 병합 대상을 따라가지 않는다.
- 이름과 설명은 문자열이고 앞뒤 공백 제거 후 비어 있지 않아야 한다. 설명은 200자 이하, 초과 시 잘라 저장하지 않고 오류.
- description과 updated_at만 수정한다. 새 도메인 생성·이름 변경·조각 재분류는 하지 않는다. 이후 라우팅에는 갱신된 설명이 사용된다.
- 성공 응답은 기존 `domains` 목록. 스키마 변경 없음.
- knowledge_record 원장 항목: `1552de6e-4c57-4b23-ac8e-55f80489c01a` (등록 시 proposed, 정본 흡수 완료와 구별).

  - **답변 끝 통합 판정 — 하네스 규칙은 하드코딩(사용자 확정 2026-09-29, 'a로 해보자 그러면')**: 사용자 제안 '그냥 두개를 섞고 하네스규칙은 하드코딩으로 못건들게 하고 규칙은 규칙으로'. 하네스 규칙 중 코드로 확실한 것(폴더 밖 차단, 검수 승인 근거, 규칙은 도구로만)은 코드가 바로 막거나 거부해 판정이 필요 없다. 의미를 봐야 하는 하네스 규칙(현재 애매하면 묻기)은 코드에 하드코딩(harness_rules.py; DB 에 없고 규칙 도구로 못 바꿈)하고, 답변 끝에 DB 의 프로젝트 규칙과 함께 한 번의 Jev 요청으로 통합 판정한다(rules-01: 전부 묶기가 가장 정확·저렴). 영수증·위반 알림에 출처(하네스/프로젝트) 표시, 하네스 규칙은 이의 제기만 가능. 알리는 경로는 분리: 하네스 규칙 = v2 기본 안내(세션 시작), 프로젝트 규칙 = 규칙 블록. '판정을 반드시 받는다' 는 것 자체가 하네스 규칙. rules 테이블의 h-* 는 제거(0007).
  - **하네스 규칙 강도 원칙(사용자 확정 2026-09-28, '좋아 우선 그렇게 하도록 하자')**: 강도는 안내(알리기만)·이어가기(답변을 끝내지 못하고 한 번 더)·차단(행동을 못 하게 막음) 세 단계. 차단은 코드로 확실히 판단되는 것에만(예: 폴더 밖 경로, 완료 문장을 검수 승인 근거로 재사용). Jev 판단 규칙은 안내·이어가기까지만(Jev 는 틀릴 수 있어 차단하면 멀쩡한 작업이 멈춤). v1 도 같은 원칙(search-debt gate 는 map 읽기 흔적만 보고 차단, record-judgement 는 판단을 적었는지만 보고 이어가기, ADR 0041: 훅은 사용자 말을 정적으로 분류하지 않음). v2 차이: 의미 판단을 작업 에이전트 자신이 아니라 Jev 가 옆에서 하고, 차단은 꼭 필요한 곳에만 둠(v1 은 게이트가 자주 걸려 작업이 끊김).
  - **애매하면 묻기 + 큰 변경은 계획 승인(사용자 확정 2026-09-28, '2랑 3 은 추천대로')**: 하네스 기본 규칙에 넣는다. 해석에 따라 코드·지식 결과가 크게 갈릴 때만 묻는다(사소한 선택은 묻지 않음). 턴 시작에 Jev 가 '해석이 갈림' 이면 안내, 답변 끝에 묻지 않고 범위를 정한 것이 보이면 한 번 이어가기. v1 의 요구사항→계획→승인→구현(ADR 0038)은 따로 두지 않고 여기에 합친다: 해석이 갈리거나 큰 변경이면 계획을 보여 주고 승인 후 구현, 작고 분명한 요청은 바로. 이유: v1 처럼 따로 강하게 두면 질문이 너무 많아짐. 계기: 실사용에서 ensure 범위를 묻지 않고 통보함. 구현 방식(규칙 정의 형태)은 미정.
  - **하네스 규칙 확인 방식(사용자 확정 2026-09-28, '이걸 해보자')**: 규칙은 조건부·동적이라 대부분 문장으로 적고 Jev 가 확인한다(사용자 '코드로 강제하기 어려운 것들이 많을태니까 jev 에게 확인'). 규칙별 판정은 해당 없음/지켰음/어겼음/모르겠음. 엔진에 묶음 크기 설정(1=규칙마다 병렬 HTTP, N=N개씩 한 요청)을 두고 실제 사례로 정확도·시간·비용을 재서 기본값을 정한다(실험 rules-01). 사용자 지적: 병렬 HTTP 라 시간·램 부담은 작고 비용은 입력 토큰 기준. 미리 알리기(지식 창에 규칙)와 사후 확인(답변 끝·완료, 확신 높은 어김만 이어가기, 모름은 안내) 병행은 제안 상태(미확정).
    - **규칙 확인 기본값(사용자 확정 2026-09-28, 'a로 가자')**: rules-01 실측에 따라 규칙을 전부 한 번에 묶어 Jev 에 물는다(20개 초과 시 20개씩 나눠 병렬). 이어가기 기준은 확신 차이 0.15 유지(오탐 이어가기 0, 기준 미달 어김은 안내). 이유: 규칙별 단독 질의는 비교 맥락이 없어 무관한 규칙을 어김으로 오탐함.
    - **판정 증거는 하네스가 자동 저장(사용자 확정 2026-09-28, 'a로 가자')**: v1 식 에이전트 자기 판단문(record-judgement 등 답변마다 쓰는 증거)은 두지 않는다. 답변 끝·완료 때 Jev 규칙 판정(해당 규칙, 지켰음/어겼음/모름, 사용한 증거)을 하네스가 영수증으로 자동 저장하고, 어긴 것으로 나왔을 때만 에이전트가 이어가며 이유를 설명하고 고친다. 이유: 자기 채점 문제(빠뜨린 걸 모르면 '필요 없음'으로 씀), 답변마다 판단문 부담·반복 의식(이 세션의 'Capture evidence: unverified' 반복) 제거, 추적 증거는 영수증으로 유지.
    - **프로젝트 규칙은 대화에서 제안·승인(사용자 확정 2026-09-28, '1은 a')**: 대화 중 사용자가 '앞으로 이렇게 해' 류로 말하면 에이전트가 규칙 문장으로 만들어 제안하고 사용자가 승인하면 들어간다. 사용자가 직접 적는 것도 가능.
    - **프로젝트 규칙 저장은 DB 만(사용자 확정 2026-09-28)**: 사용자 'db 만 쓰는게 좋아 그래야 딱 우리 규칙만 보지 아니면 오염될것같거든?? 우리 하네스는 기본적으로 모든게 우리 하네스 + db 니까'. 프로젝트 규칙의 저장·정본은 하네스 DB 뿐이며, 프로젝트 저장소에 규칙 파일·자동 내보낸 사본을 두지 않는다(파일이 있으면 다른 도구·사람의 규칙과 섞여 오염될 수 있음). 하네스 기본 규칙은 하네스 배포본에 포함(고정). 원칙: lazy-harness 는 하네스(코드·배포본) + DB 로만 동작한다.
    - **규칙은 소화를 거치지 않고 규칙 도구로(사용자 정정 2026-09-28)**: 사용자 '규칙은 소화모듈을 통하는게 아니야 우리가 이제 이렇게 하는거야 라고 말하거나 하면 알아듣고 알아서 규칙을 생성하는 툴을 사용하는거지', '규칙은 삭제 수정 생성 등등이 가능해야하잖아'. 규칙은 지식 모듈의 원장·검수·소화 흐름을 타지 않는다. 사용자가 '이제 이렇게 하자' 류로 말하면 에이전트가 알아듣고 규칙 모듈의 규칙 도구로 생성·수정·삭제한다. 저장은 같은 DB 의 규칙 전용 공간(지식 테이블과 분리 — 검색·판정 오염 방지), 변경 이력 보존. 이유: 규칙은 에이전트 행동을 묶는 것이라 자동 흡수 대상이 아니고, 의도는 사용자 말에서 직접 온다. 근거·적용 전 확인은 아래 '규칙 JSON 스키마와 생성 확인'.
    - **규칙 JSON 스키마와 생성 확인(사용자 확정 2026-09-28, '우선 니 추천대로')**: 사용자 제안 'jev 가 json 도 받잖아 … json 형식으로 스키마 짜두면'. 규칙 = {id, when(조건), must(해야 할 것), scope?(적용 범위), check_at(answer_end/complete 등), strength(notice/continue/block), code_check?(검사 부품+인자), source(사용자 발화 원문·시각)}. 에이전트가 사용자 말을 규칙 도구 입력(이 스키마)으로 넣는다. 생성 시 ① 코드 검사: 필수 칸, strength=block 은 code_check 있을 때만(강도 원칙을 스키마가 강제), 하네스 기본 규칙 id 덮기 거부 ② Jev 확인: 기존·기본 규칙과 충돌/중복/기본 약화 비교(scope 가 겹치는 것 위주), 최근 판정 영수증으로 시험 판정해 판정 불가(모름 대부분)·과도하게 넓음(항상 해당) 확인. 문제없으면 바로 적용하고 한 줄로 알림, 문제 있으면 적용하지 않고 사용자와 결정(기본 규칙 약화는 반드시 사용자 확인). 사후 확인은 조건 충족 → 행동 이행의 두 단계로 판정(rules-01 의 무관 규칙 오탐 완화 기대). 규칙 블록에 전부/관련만 넣을지는 미정.
      - **규칙 스키마 정리(사용자 확정 2026-09-28, '추천안으로 우선 하자', 위 스키마를 대체)**: 에이전트가 적는 칸 = when(조건, 항상이면 '항상'), must(해야 할 것, 금지는 '~하지 않는다'), level(must 반드시 / should 권장), why?(사용자가 말한 이유), code_check?(정해진 부품 목록에서만, 부품이 자기 확인 시점을 가짐), source(사용자 발화 원문). id 는 DB 가 자동 생성, 접두사 h-(하네스 기본)/p-(프로젝트)로 기본 규칙 덮기를 코드가 막음. 상태·버전·변경 이력·시각은 규칙 도구와 DB 가 관리. 변경: scope 삭제(when 과 중복), check_at 삭제(Jev 판정은 답변 끝·완료에 항상, 코드 검사 시점은 부품이 가짐), strength → level(강제 방식은 엔진이 정함: must+code_check=차단, must+Jev=이어가기, should=안내 — 강도 원칙이 구조적으로 지켜짐), why 추가(경계 상황 판단에 도움).
      - **예외 칸 unless(사용자 확정 2026-09-28, 'a로 가자')**: 스키마에 unless?(예외 조건, 예: '단 로컬 테스트 DB 는 제외')를 추가한다. v1 policies.json 비교에서 가져옴(rollback.criteria 유사). v1 은 조건이 상황 태그(appliesTo)·본문은 별도 문서·level 5단계(중요도와 강제 방식 혼합)·파일 저장이었고, v2 는 자연어 when/must 를 Jev 가 판단·must/should·DB 만. evidence 배열은 변경 이력으로, promotion 은 level+code_check 자동 결정으로 대체.
