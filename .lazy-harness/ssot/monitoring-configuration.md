## Authority and compatibility

The user selected public SDK + schema/validator + generic conformance, then explicitly chose an independent baseline with optional Fabric integration. Serialized `contractVersion:1` is separate from the existing core v0, private package version and Pi host version. Module binding versions must match exactly. The source package remains private; publication, dependency installation, actual collection and an optional Fabric connector are not enabled.

`schema.ts` owns required source kind/scope pairs, IDs, version, goals, references, modules/settings and component limit fields. `configuration.schema.json` is generated by the declared build; `MonitoringConfiguration` derives statically from the same native schema. The public README lists field bounds/defaults and stable failure categories. Module settings use a host-supplied native TypeBox schema; `Value.Clone` preserves non-enumerable kind metadata whereas JSON cloning does not. Readonly normalized data and module settings are frozen at runtime.

Host bindings exclusively own module factories/grants/destinations, receiver/judge IDs, admitted source scopes, module count and ceilings. Explicit requests must stay within ceilings; omitted fields still inherit an existing ceiling. Default-off construction does not create an inference/data-disclosure grant. Core-only source identity and engine factory are host-issued; the Pi factory receives an explicit bridge and a separately permitted start context. Missing Fabric-labelled bindings are ordinary missing bindings, not fallback triggers.

## Model profile configuration authority

`packages/lazy-harness-pi/monitoring/model-schema.ts` is the single native TypeBox authority for separate `modelConfigVersion:1` profile data. Static readonly types, normalized defaults/validation and the generated `model-profiles.schema.json` derive from it. Monitoring configuration v1 remains unchanged and chooses a symbolic judge binding as before; the host may supply a configured model router behind that binding.

Profile data chooses explicit backend/version/provider/model/role/parameters and requested limits/routes; it does not own credentials, installation, HTTP endpoints, provider support or permissions. The host owns an exact backend capability/parameter schema, roles, complete ceilings, max profile count and sum-of-caps concurrency admission. Unknown settings reject, known credential key forms reject, native referenceThreshold is not silently accepted by JSON adapters. Native metadata survives cloning for defaults. Host driver versions/identity and normalized profile/router fingerprints must accompany evaluation; a changed model/config cannot inherit an older model's>=95% score.

Worker configuration is module-owned: a module's own validated settings may name an admitted worker profile, then trusted code explicitly calls typed invokeWorker. The model router does not generate jobs, run arbitrary code, modify active Pi model settings or create a global registry. Timer values must be finite safe platform timers; reservations cover driver-call attempts/input+output token maxima and host-estimated USD, not invoice/HTTP verification. Credentials and actual retry/redirect/metering enforcement remain host-side.

Implementation/verification: `model-schema.ts`, `model-adapters.ts`, `models.ts`, public `/monitoring/models` subpath, the existing artifact generator and `models.md` are mapped in the monitoring SDD. Corresponding model-schema/model-adapters/models/shared-schema tests, actual SDK synthetic tests and isolated public imports protect admission, defaults, unsupported settings, exact views/evidence, physical drain and reservation limits. The three surfaced utility candidates were confirmed B/existing component ownership; registry.xml remains unchanged.
