# Pi/OMP Global Bootstrap + Project Activation Plan

Status: planned
Created: 2026-06-22

## Confirmed direction

User-confirmed direction: install the lazy-harness Pi/OMP package globally as the runtime bootstrap, but activate behavior per project.

Operational split:

- Global bootstrap: Pi/OMP loads `@lazy-dinosaur/lazy-harness-pi` once from the lazy-harness source package path.
- Project activation: a project opts in by having `.lazy-harness/bin/lazy` and project-local prompt/config files generated by `lazy init` or a dedicated activation command.
- Non-harness projects: the extension remains loaded but no-ops when walking up from `ctx.cwd` cannot find `.lazy-harness/bin/lazy`.
- Long/static project prompts: project-local `.pi/APPEND_SYSTEM.md` and `.omp/APPEND_SYSTEM.md`.
- Dynamic reminders: `before_agent_start` only injects short turn-specific guard/reminder text for activated projects.

## Evidence checked

- `.lazy-harness/spec/platform/pi-agent-package.md` currently specifies the Pi/OMP extension bridge and wrapper install contract.
- `.lazy-harness/decisions/0047-pi-omp-shared-package-separate-install-ux.md` currently separates Pi wrapper UX from OMP plugin UX.
- `packages/lazy-harness-pi/extensions/lazy-harness/index.ts` already no-ops when `findLazyRoot(ctx.cwd)` cannot find `.lazy-harness/bin/lazy`.
- `.lazy-harness/scripts/pi-package.ts` already supports Pi global install dry-run, Pi local install dry-run, OMP plugin install dry-run, and non-mutating doctor commands.
- `.lazy-harness/scripts/self-test.py#check_pi_package_layout_and_contract` already covers package manifest, wrapper dry-runs, before-agent-start injection, tool-call blocking, and root-scoped recent tool state.

Focused verification run on 2026-06-22:

- `lazy pi install --global --dry-run --format=json` -> `pi install <package> --no-approve`.
- `lazy pi install --local --dry-run --format=json` -> `pi install <package> -l --approve`.
- `lazy omp install --dry-run --format=json` -> `omp plugin install <package>`.
- `lazy pi doctor --no-smoke --format=json` -> non-mutating ok.
- `lazy omp doctor --no-smoke --format=json` -> non-mutating ok.
- Synthetic `before_agent_start` from a temp dir without `.lazy-harness/bin/lazy` returned `undefined`, proving current global bootstrap can no-op outside activated projects.

## Target user experience

### Install bootstrap once

```bash
.lazy-harness/bin/lazy pi install
.lazy-harness/bin/lazy omp install
```

Expected default after this change:

- `lazy pi install` defaults to global Pi package install.
- `lazy pi install --local` remains available for explicit project-local package attachment.
- `lazy pi install --global` remains accepted as explicit spelling.
- `lazy omp install` keeps current OMP plugin registry behavior because OMP persistent plugin install is already global/user-level.

### Activate a project

```bash
/path/to/lazy-harness/.lazy-harness/bin/lazy init --target /path/to/project
/path/to/lazy-harness/.lazy-harness/bin/lazy agent activate --target /path/to/project
```

`lazy init` should either run activation by default or print the exact activation command. The dedicated activation command can be introduced if keeping `lazy init` focused is cleaner.

Activation artifacts:

- `.lazy-harness/` managed framework files and host-local records.
- `.pi/APPEND_SYSTEM.md` for Pi project-local static prompt additions.
- `.omp/APPEND_SYSTEM.md` for OMP project-local static prompt additions.
- `.git/info/exclude` entries for `.pi/` and `.omp/` when those directories contain local-only runtime config.
- Optional project marker such as `.lazy-harness/ssot/agent-runtime.md` only if later code needs an explicit activation state beyond `.lazy-harness/bin/lazy` presence.

## Non-goals

- Do not put long lazy-harness rules into global Pi/OMP prompt files.
- Do not make non-harness repositories run lazy-harness hooks.
- Do not rely on OMP `package.json#pi` fallback; keep explicit `package.json#omp`.
- Do not make package publication or standalone extraction part of this change.
- Do not remove `--local`; keep it as an explicit advanced path.

## Detailed task plan

### Phase 1 — Contract updates

1. Update `.lazy-harness/spec/platform/pi-agent-package.md` install contract:
   - Define global bootstrap + project activation.
   - State that non-harness cwd no-ops are required behavior.
   - State that project-local prompt files own long/static prompt text.
   - Keep OMP plugin registry semantics explicit.
2. Update `.lazy-harness/decisions/0047-pi-omp-shared-package-separate-install-ux.md`:
   - Add 2026-06-22 amendment: default UX shifts from explicit Pi scope to global bootstrap with project activation.
   - Preserve separate Pi/OMP wrapper UX.
3. Update `.lazy-harness/tests/pi-agent-package.md`:
   - Add regression cases for default Pi global install command.
   - Add regression case for non-harness no-op.
   - Add regression case that activation owns `.pi/APPEND_SYSTEM.md` and `.omp/APPEND_SYSTEM.md` guidance.

### Phase 2 — CLI and wrapper behavior

1. Change `.lazy-harness/scripts/pi-package.ts`:
   - `lazy pi install` defaults to global scope.
   - `lazy pi remove` should still require explicit scope unless a safe default is deliberately confirmed; safer default is keep explicit remove scope.
   - `lazy pi list` can keep local default or show both scopes if implemented; do not obscure where activation came from.
   - Help text must describe global bootstrap and project activation.
2. Update `.lazy-harness/bin/lazy` help/dispatch text if needed.
3. Keep `lazy omp install` unchanged except docs wording; it already maps to global/user plugin registry semantics.

### Phase 3 — Project activation surface

1. Decide implementation surface:
   - Preferred: extend `lazy init` to write project-local Pi/OMP prompt files when Pi/OMP support is requested.
   - Alternative: add `lazy agent activate` for existing projects that already have `.lazy-harness`.
2. Generate project-local prompt files:
   - `.pi/APPEND_SYSTEM.md`
   - `.omp/APPEND_SYSTEM.md`
   - Content should be concise pointers to `.lazy-harness/AGENTS.md` / project records, not a second full copy of all rules.
3. Ensure `.git/info/exclude` includes `.pi/` and `.omp/` if local runtime config is written.
4. Add activation command dry-run output listing files it would create/update.

### Phase 4 — Extension hardening

1. Keep current non-harness no-op invariant in `before_agent_start`, `tool_call`, and `tool_result`.
2. Reduce fallback reminder body if static project prompt now carries stable rules.
3. Ensure globally exposed commands behave safely outside activated projects:
   - `/lazy-map`, `/lazy-doctor`, `/lazy-test`, `/lazy-sync`, `/lazy-update`, `/lazy-import-antigravity-mcp` should notify that `.lazy-harness/bin/lazy` was not found and do nothing.
4. If OMP globally exposes skills/prompts in all projects, document this and keep skill bodies self-gating on `.lazy-harness` evidence before mutation.

### Phase 5 — Regression coverage

1. Extend `.lazy-harness/scripts/self-test.py#check_pi_package_layout_and_contract`:
   - `lazy pi install --dry-run --format=json` expects global install command.
   - `lazy pi install --local --dry-run --format=json` still expects local install command.
   - fake runtime from non-harness cwd expects `before_agent_start === undefined`.
   - activation prompt file generation is covered if implemented in `lazy init` or new command.
2. Add or update TDD record rows in `.lazy-harness/tests/pi-agent-package.md`.
3. Run focused self-test for package layout/contract after edits.
4. Run `lazy pi doctor --no-smoke --format=json` and `lazy omp doctor --no-smoke --format=json`.
5. Smoke current-host Pi/OMP install only after dry-runs match the new contract.

### Phase 6 — Documentation and sync

1. Update `packages/lazy-harness-pi/README.md`:
   - Bootstrap once globally.
   - Activate per project.
   - Keep local install documented as advanced/explicit.
2. Update root README if it references Pi/OMP install defaults.
3. Regenerate record index if records change.
4. Sync downstream hosts only after source tests pass.

## Risks and checks

| Risk | Check |
|---|---|
| Global package exposes skills/prompts everywhere | Verify Pi/OMP UI behavior; ensure command handlers and skill instructions no-op without `.lazy-harness` evidence |
| Token waste from repeated dynamic reminder | Keep static prompt in project-local APPEND files; reduce `before_agent_start` fallback to short state-only text |
| OMP lacks project-local plugin enable/disable | Treat OMP plugin install as global bootstrap; activation remains `.lazy-harness` presence + project-local `.omp/APPEND_SYSTEM.md` |
| Existing users expect explicit Pi scope | Keep `--local`/`--global`; make default only for `install`, not destructive `remove` |
| Team pollution from `.pi`/`.omp` files | Write runtime config as local/untracked by default and update `.git/info/exclude` |

## Acceptance criteria

- Non-harness project with global package installed receives no lazy-harness hook mutation or reminder injection.
- Activated project receives project-local static prompt plus short dynamic reminder.
- `lazy pi install` dry-run defaults to global bootstrap.
- `lazy pi install --local` still works.
- `lazy omp install` behavior remains explicit OMP plugin install.
- Focused package self-test passes.
- Pi/OMP doctor no-smoke stays non-mutating and passes.
