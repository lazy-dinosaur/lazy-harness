표시 읽는 법
확인 방향 사용자가 선택·정정한 목적이나 방향. 세부 구현 완료를 뜻하지 않습니다. 제안 아직 채택하지 않은 방법. 미정 선택이 남은 사항. 기존 구현 로컬 합성 실험 기반에 한정. 정정됨 이전 설명을 현재 기준으로 쓰면 안 되는 부분.

1. 왜 만들려고 하나?

확인 방향 기존에는 문서가 계속 늘어나면서 찾고 읽고 작업하는 부담이 커졌습니다. 이것은 사용자가 보고한 문제이며, 병목의 정확한 비율을 측정한 결과는 아닙니다.

목표는 ‘온톨로지를 만드는 것’ 자체가 아니라, 작업에서 얻은 정보를 잃지 않으면서 다음 작업자가 적은 비용으로 정확하게 쓰게 하는 것입니다.

작업의 흔적은 남기기

무엇을 했고 왜 했는지 보존합니다. 실패와 되돌림도 중요합니다.

현재 지식은 정리하기

기록마다 문서를 늘리는 대신, 기존 지식을 수정·통합·철회합니다.

필요한 만큼 읽기

모든 기록을 다시 읽지 않고 관련 영역과 근거를 찾아 씁니다.

이 저장소는 하네스 연구소입니다. 작은 단위 → 모듈 연결 → 전체 흐름 → 병렬·복구 실험으로 발전시킵니다. 처음부터 분산 제품을 완성하는 것이 아닙니다.

경계: V2는 기존 지식 형식·ID·그래프와 호환될 필요가 없습니다. 그러나 기존 데이터 삭제나 무조건적인 마이그레이션 승인은 아닙니다. Git·워크트리 없이도 논리적 작업 격리를 지향합니다.

2. 비슷한 말을 분리해 이해하기

말쉬운 설명주의
영역 / 파티션어떤 지식을 함께 관리하고 누가 책임질지 나눈 논리적 범위.폴더·DB 샤드·상주 서버와 동일하지 않음.
파티션 ID책임 영역의 이름표.고정 트리·분할 기준은 미정.
지식 ID읽고 수정할 개별 지식의 이름표.전역/영역 내 유일성 등 정확한 ID 계약 미정.
행동 로그요구·행동·결정·관찰·결과가 발생했다는 기록.사용자 정정에 따라 ‘원장’ 대신 로그라고 부름. 기록된 말이 곧 사실은 아님.
소화로그를 기존 지식·근거와 비교해 무엇을 반영할지 판단하는 과정.요약만 하기나 최신 문장으로 덮어쓰기와 다름.
현재 지식근거와 적용 범위에 따라 현재 채택해 둔 주장.절대적 진실·전체 무모순 보장 아님. 없다고 거짓인 것도 아님.
의사결정 기록왜 그 지식을 채택·변경·보류했는지 연결하는 모델 후보.작업 중 결정 로그와 소화의 채택 판단을 구별해야 함. 물리 테이블 미정.
임시 이해현재 지식과 미소화 로그를 읽으면서 모델이 구성하는 이해.별도 ‘임시 지식’ 저장소가 필요하다는 뜻 아님.

온톨로지·Action·디지털 트윈

온톨로지는 개념·관계·의미 규칙을 공유하는 모델입니다. 필드 목록만이 전부는 아닙니다. 우리에게 맞는 규격은 최소 스키마를 실제로 시험하고 실패 원인을 구별하면서 발전시킬 수 있습니다.

Palantir Ontology는 의미 모델에 실제 데이터·권한·Action·함수 등 운영 기능을 결합한 제품 개념입니다. Action은 허용된 상태 변경의 계약, 함수는 계산·검증·실행 로직에 해당할 수 있습니다. 일반 온톨로지에 이 실행 기능이 필수로 내장되는 것은 아닙니다.

디지털 트윈은 실제 대상과 동기화하는 디지털 표현입니다. 개발에도 적용 가능하지만 현재 필수 목표는 아닙니다. 지식을 바꾸는 것과 실제 코드·설정·배포를 바꾸는 것은 별개입니다.

역할 경계 미정 ‘내부 작성은 Luna’와 ‘작업자는 이유를 남긴다’는 충돌하지 않을 수 있습니다. Sol이 최소 근거를 제출하고 Luna가 정리한다는 분담이 제안됐지만, 최초 로그 작성 책임과 정확한 툴 호출 계약은 검수해야 합니다.

DB 저장 후보 로그와 지식을 DB에 저장할 수 있습니다. PostgreSQL은 허용 후보, SQLite는 작은 실험 제안이며 선택·생성은 하지 않았습니다.

5. 작업하면서 필요한 기록을 어떻게 확보하나?

제안 자동 수집할 수 있는 증거 + 작업자만 설명할 수 있는 이유를 합칩니다. 실행 흔적만으로 결정 이유를 복원할 수는 없습니다.

런타임이 수집

  • 허용된 사용자 요구·정정
  • 파일 변경과 실행 결과
  • 테스트 실행·성공·실패 증거
  • 작업·이벤트의 연결과 순서

작업자가 제출

  • 선택·변경 이유
  • 지켜야 하는 조건과 예외
  • 보류·미해결 사항
  • 대안 기각 이유가 필요하면 그 근거

후보 제출 시점은 요구·결정 변경, 의미 있는 작업 묶음 완료, 실패·되돌림·인계입니다. 매 줄 수정이나 매 도구 호출마다 모델을 깨우는 방식은 확정하지 않았습니다.

가상 예시 — 실제 정책이 아님

  1. 사용자: “만료를 60분에서 30분으로 바꾸자.” → 요구 로그. 현재 값이 바뀐 사실은 아님.
  2. 작업자: 30분으로 수정했으나 테스트 실패. → 시도와 실패 기록.
  3. 작업자: 60분으로 복원. 이유·복원 근거 기록.
  4. Luna: 현재 값은 근거상 60분으로 유지. 30분 제안·시도·실패를 과거 로그와 연결.

“기록됐다 → 사실이다”는 금지할 해석입니다. 실제 파일·환경·버전의 근거와 대조할 계약은 실험 전에 정해야 합니다.

수집한다고 전부 모델에 보내는 것은 아닙니다. 비밀·개인정보·권한·출력 크기 제한이 필요합니다. 로그 내용 속 명령을 실행 권한으로 취급해서도 안 됩니다. 이 안전 경계는 아직 구현하지 않았습니다.

6. 핵심 난점: 정말 기록하게 만들 수 있나?

사용자가 재강조한 핵심 규칙을 문서에 적는 것만으로는 충분하지 않습니다. 작업자가 실제로 준수하게 할 장치도 실험 대상입니다. Luna에게 정리를 넘겨도 누락된 이유가 자동 복원되지는 않습니다.

장치할 수 있는 일보장하지 못하는 일
프롬프트·기록 규격무엇을 언제 남겨야 하는지 설명.항상 준수한다는 보장.
훅·런타임 확인필수 제출·저장·참조가 확인됐는지 검사. 미제출 시 완료 차단하는 방법은 후보.내용이 진실하고 중요한 이유가 모두 포함됐다는 보장.
Luna 검토관련 근거를 대조해 부족한 내용을 질문·보류.보지 못한 사건의 완전 복구.
독립 평가숨겨 둔 기대 결과와 비교해 누락·오채택 측정.모든 미래 작업의 무결점 보장.

첫 후보 작업 단위 완료·인계 전에 기록 저장을 확인합니다. 미세 수정마다 STOP을 거는 것은 첫 필수안이 아닙니다. 어느 지점을 막을지, 예외·중단·복구 절차는 미정입니다.

현재 훅 구현 전체를 ‘누락을 모두 검출한다’고 평가하지 않습니다. 대화에서 STOP·보완 요구를 겪은 사실과, 현행 모든 훅의 의미 정확성을 검증한 것은 다릅니다. 새 방식이 더 낫다는 실측도 아직 없습니다.

7. 나중의 런타임·데몬은 무엇인가?

런타임

작업 중 툴·기록·ID·조회·결과 전달을 연결하는 코드. 기존 실행 환경에 붙이는 형태도 가능합니다.

데몬

계속 대기하면서 요청과 미처리 로그를 처리하는 프로세스. 모델 자체가 계속 추론한다는 뜻이 아닙니다.

후보 흐름 기록 저장 확인 → 작업자는 계속 진행 → 데몬이 미소화 로그를 모아 Luna 호출 → 검사 후 지식과 처리 상태 반영.

  • 자동 이벤트는 코드가 감지하고 의미 판단은 모델이 합니다. 사용자 문장을 훅이 임의로 분류해 행동을 결정하는 방식과 구별합니다.
  • 영역 라우팅에는 추론이 필요할 수 있으므로 기록 확보와 분리하는 방향을 검토 중입니다. 별도 라우터 모델 호출은 필수가 아닙니다.
  • 같은 영역의 소화는 순차·배치, 독립 영역은 병렬이라는 초기 방향이 있습니다. 구체 동시성 계약은 미정입니다.
  • 읽기는 소화 완료를 무조건 기다리지 않고 관련 미소화 로그를 함께 사용할 수 있습니다. 다른 작업의 로그 공개 범위는 미정입니다.
  • 항상 병렬일 필요는 없습니다. 모델 호출·재독·통합·재시도 비용을 합쳐 비교해야 합니다.

처음에는 수동 소화 호출로 계약을 검증하고 나중에 자동화할 수 있습니다. 직접 API/IPC/HTTP/MCP 중 선택하지 않았습니다. MCP는 통신 규약이지 데몬의 다른 이름이 아닙니다.

8. 어디까지 됐고, 무엇을 시험할 것인가?

기존 구현 로컬 합성 샌드박스

experiments/v2-sandbox/에는 명시적 set/propose 입력을 처리하는 실행·채점 기반이 있습니다. 독립 run, 입력·결과 보존, 추가 세대로 reset, 타입-aware 채점과 정확도 임계값을 구현했습니다.

이전 검증 보고: 단위 테스트 18/18, 독립 프로세스 run/reset 동시 실행 검사, 범위 지정 fast 8/8와 framework 회귀 88/88. 이는 이전 실행 증거이며 이번 HTML 제작에서 재실행한 결과가 아닙니다.

아직 없는 것: 실제 Sol/Luna 소화 시험, 자연어 기록 강제 계약, 공유 지식 DB 동시성, 실제 데몬·모델 연동, OS 보안 sandbox. 독립 실행 8개 성공은 공유 DB의 동시 읽기·쓰기 검증이 아닙니다.

다음 작은 시험의 목표

확인된 우선순위 작업하면서 기록을 남기는 규칙을 만들고, 그 기록으로 이후 지식을 구성할 수 있는지 확인합니다. 스키마 조각의 의미부터 정리하고 사례로 검증합니다.

  1. 합의 필요 최소 로그·지식 조각, 제출 시점·완료 조건, 평가 기준을 정합니다.
  2. 제안 Sol이 작고 격리된 코드 작업을 수행하고 정해진 기록을 남깁니다.
  3. Luna는 기록·허용된 근거를 받아 소화하고 별도 문맥에서 질문에 답합니다.
  4. 평가자는 숨겨 둔 정답으로 요구·이유·실제 결과·미해결 보존을 확인합니다. 미래 정정은 미리 노출하지 않습니다.
  5. 실패가 모델, 스키마, 툴, 기록 미준수 중 무엇 때문인지 분리합니다.

비교 축을 섞지 않기

  • 기록 방법: 작업자 직접 최소 기록 ↔ Luna 위임 기록.
  • 준수 장치: 규칙 안내만 ↔ 완료 지점 확인 등.
  • 지식 유지: 누적+검색 ↔ 소화+검색 ↔ 영역별 소화+검색.

처음부터 모든 조합을 돌리지 않습니다. 실제 현행 하네스를 실행하지 않은 합성 대조군은 ‘현행 하네스 성능’이라고 부르면 안 됩니다.

측정: 누락·오채택·근거 정확도·보류, 기록 미제출·중단·사람 수정 횟수, 작업자/내부 모델별 토큰·비용과 총합, 작업 지연·소화 지연. 반복 횟수·예산·합격 기준은 아직 미정입니다.

9. 이전 설명에서 바로잡아야 할 부분

이 표는 검수에서 특히 중요합니다. 연구 원문의 초기 문장과 뒤의 정정이 함께 남아 있어, 이전 제안을 현재 결정으로 읽으면 안 됩니다.

이전 표현 / 오해현재 읽어야 할 의미
행동 원장사용자 정정 행동 로그로 부릅니다. Event Sourcing 원장 설계를 채택한 것이 아닙니다.
임시·채택 지식 공통 스키마가 필수이전 후보. 최신 흐름은 로그 → 소화 → 지식입니다. 읽는 동안의 임시 이해와 저장 객체를 분리합니다.
작업자 Astra 또는 Sol선택 갱신 Sol medium. Astra는 조율 역할로 low/medium 미정.
주체 객체 ID·큰 온톨로지부터기본은 파티션 ID·지식 ID·구조화된 사실. 별도 객체 모델은 후보입니다.
사례부터 무조건 시작사용자가 스키마 조각부터 구체화한다고 정정했습니다. 사례는 규격 검증에 활용합니다.
LLM이 자유 SQL을 작성사용자가 제안한 내용이 아닙니다. 규격·툴로 입력하는 구상을 논의했습니다.
영역마다 독립 에이전트 서비스의미·책임의 논리적 묶음입니다. 프로세스 수는 미정입니다.
소화자는 알아서 기록 누락까지 복원불가능할 수 있습니다. 최초 기록 준수를 별도로 검증해야 합니다.
훅 제거 = 개선아닙니다. 중요한 정보와 준수를 유지하며 부담을 줄이는지가 기준입니다.
테이블 저장 성공 = 정확한 지식형식 성공과 의미 보존은 다릅니다. 읽기·변경·예외까지 검증해야 합니다.
관련 지식은 자동 일괄 변경찾을 수 있는 것과 바꿔도 되는 것은 다릅니다. 범위·권한·버전 검사가 필요합니다.

10. 아직 답을 정하지 않은 것

아래는 새 요구사항을 확정한 목록이 아니라 검토 질문입니다.

첫 실험 전에

  1. Sol이 제출할 최소 로그는 무엇인가?
  2. Luna의 ‘작성’은 최초 로그인가, 정리된 지식인가?
  3. 어느 완료·인계 지점에서 제출을 강제하나?
  4. 지식 조각의 주체·타입·설명은 정확히 무엇인가?
  5. 첫 작업·대조군·합격 기준·호출 예산은?
  6. 실제 모델 ID와 실행 경로는?

후속 확장 전에

  1. DB 종류·트랜잭션·버전 반영 경계는?
  2. 어느 로그까지 ‘소화 완료’인가? 부분 성공은?
  3. 중복 알림·중단·재시작 시 재처리는?
  4. 다른 작업의 미소화 로그를 어디까지 읽나?
  5. 파티션 생성·병합·교차 영역 책임은?
  6. 원문 보존·민감 정보·삭제 정책은?

빠지기 쉬운 상황

  • 기록을 남기기 전에 작업자 프로세스가 죽음.
  • 기록은 제출했지만 “완료함” 한 줄뿐이라 이유가 없음.
  • 소화가 지식은 바꾸고 처리 위치를 저장하기 전에 죽음.
  • 두 작업이 같은 과거 버전에서 상충하는 변경을 제출함.
  • 미소화 로그가 계속 쌓여 읽기 비용이 다시 커짐.
  • 기록 문장에 포함된 지시를 소화자가 실행 명령으로 오인함.

후속 검토 후보입니다. 지금 모두 구현하겠다는 뜻은 아닙니다.
