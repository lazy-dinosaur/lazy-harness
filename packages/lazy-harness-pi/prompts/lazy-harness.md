# Lazy-Harness Prompt

Use the host-local `.lazy-harness` records as the source of truth before host-specific claims or mutations.

1. For a new host-dependent Pi work unit, prepare the dedicated `lazy-harness.record-reader` using `lazy_reader_request` with the exact top-level root/revision/model/evidenceEpoch/maxReadCalls/maxRequestedLines/maxLinesPerRead/task envelope. Use explicit `model: openai/gpt-6-luna:low` unless a task-specific override was approved. Do not preselect record nodes. Pass the returned `details.request` unchanged to `agents.spawn` inside `fabric_exec`, and return its handle. This is a fresh read-only Pi Fabric worker; pi-subagents is not required. Do not pass old Agent Contract/acceptance/output/artifacts/toolBudget flags. OMP retains its separately exposed native task transport.
2. While the Reader performs one complete map overview, concrete drill-down, and task-relevant canonical record reads, use the Parent lane for source/tests or immediately needed behavior. Discover existing source paths with native `find`/`grep` before any Parent body read; never guess a filename. Prefer native `read`/`grep`/`find` or a single simple read-only shell command; do not use redirection (including `2>/dev/null`), compound commands, or display pipelines. Prefer native tools. Implementation under `.lazy-harness/scripts/` is Parent source, not a canonical record directory. Parent remains the decision, mutation, integration, validation, and final-answer owner.
3. Before planning, mutation, or host-specific completion, call `agents.wait({id: handle.id})` (or `agents.join`) and return the full result to Parent context. Consume its content-bearing Reader packet, then call `lazy_reader_join` with the actual status/result marker and revision/evidence epoch. Normally omit run ID, counters and recordPaths; runtime state supplies the full successful-read set and budget ledger. Completion/status/automatic notification alone is not a join. No status/shell polling. If a lane fails, stop new work, drain the Fabric result and answer once. Missing/failed/incomplete/conflict/stale Reader results enable bounded direct fallback, never require reinstalling pi-subagents. A prepared request whose spawn failed can be closed with status failed to enter fallback. OMP native yielded-content handling remains unchanged.
   The task uses exact `root:`, `revision:`, `model:`, `evidenceEpoch:`, `maxReadCalls:`, `maxRequestedLines:`, `maxLinesPerRead:`, and `task:` lines; task model must equal the explicit launch model. The packet marker is `LAZY_HARNESS_READER_RESULT: complete|incomplete|conflict`. Runtime checks include `maxObservedReadLimit` and failed-tool count; child self-reports are not authority.
4. If the dedicated Reader is unavailable or fails, run one `.lazy-harness/bin/lazy map --overview --complete --format=md`, drill one copied concrete node, and read the governing digest plus exact linked source/test directly.
5. Reuse unchanged joined/grounding evidence across later normal messages. Re-ground only for a new session, real scope change, explicit steer, changed/deleted governing record, or root/revision/epoch mismatch.
6. Never pass raw user text, long natural-language strings, or invented `--query` flags to `lazy map`; map/index output is navigation, not read proof.
7. Finish a coherent mutation batch before validation. Run `lazy check` once at a deliberate checkpoint, at most one focused/affected check per changed-behavior batch, and one final `lazy validate --plan standard`. Reserve direct `lazy test` for explicit fresh regression or commit/push/release gates.
8. Keep green validation output to status/count/time; store detailed logs outside the conversation. A post-response advisory must not replace the substantive Parent answer in non-interactive print mode.
